## What this PR is

Five federated `*_tvos` FlutterFire implementation packages — `firebase_core_tvos`, `firebase_auth_tvos`, `cloud_firestore_tvos`, `firebase_storage_tvos`, `firebase_messaging_tvos` — generated by `flutter-tvos plugin port` and finished by hand. Each is:
- A **one-line Dart re-export** of the upstream app-facing package (no Dart API duplication — correct, since FlutterFire has no per-platform Dart override).
- A **vendored copy of the upstream native Obj-C/Swift plugin**, with tvOS-unavailable APIs disabled behind `#if TARGET_OS_TV`.
- A **podspec** depending on the native Firebase Apple SDK (tvOS-supported since 8.9.0) and on `firebase_core_tvos` instead of the iOS-only `firebase_core` pod.

## Critical / High-severity Issues

> **Reviewer note on severity:** the silent-failure specialist classifies #1 and #2 below as **CRITICAL** because the Dart return type is non-nullable and the failure is a *deterministic* thrown `PlatformException`, not a maybe-hang. I'm presenting them at the top but flagging that the *blast radius* is narrow — phone auth is entirely unusable on tvOS regardless — so whether these block merge is a maintainer call. Either way the fix is trivial (~4 lines each) and should land before publish.

### 1. `verifyPhoneNumberApp` returns `completion(nil, nil)` on tvOS → deterministic `null-error` PlatformException
`packages/firebase_auth_tvos/tvos/Classes/FLTFirebaseAuthPlugin.m:1995-1998`

On tvOS this logs and calls `completion(nil, nil)` — **success, no error, nil result**. Unlike every other disabled auth path (MFA/TOTP/OAuth-provider/reCAPTCHA), which correctly return an `unsupported-platform` `FlutterError`, the phone path returns nothing.

**Consequence (verified against upstream `messages.pigeon.dart`):** the Pigeon method's Dart return type is **non-nullable `Future<String>`** (the event-channel name the `codeSent`/`verificationCompleted`/`verificationFailed` callbacks subscribe to). A null reply therefore **deterministically throws** `PlatformException(code: 'null-error', message: 'Host platform returned null value for non-null return value.')` — the app never learns "phone auth is unsupported on tvOS"; it gets an opaque error and no verification callback ever fires.

**This contradicts the PR's own PORTING_REPORT**, which claims phone verification is "disabled" like the MFA stubs — but the MFA stubs return `unsupported-platform`, whereas this returns nil/nil. The porter summary also reports "Native regions disabled: 0 / Manual review items: 0" while the file has ~30 `TARGET_OS_TV` guards — so these branches were never surfaced for review.

**Fix:** mirror the MFA stubs 30 lines away —
`completion(nil, [FlutterError errorWithCode:@"unsupported-platform" message:@"Phone number verification is not supported by the Firebase SDK on tvOS." details:nil]);`

### 2. `updatePhoneNumberApp` returns `completion(nil, nil)` on tvOS → same `null-error` throw
`packages/firebase_auth_tvos/tvos/Classes/FLTFirebaseAuthPlugin.m:2454, 2507-2511`

The port added `&& !TARGET_OS_TV` to the `#if TARGET_OS_IPHONE` guard; since tvOS *is* `TARGET_OS_IPHONE`, this is a genuine new divergence (previously tvOS took the real branch). The Pigeon return type is non-nullable `InternalUserDetails`, so `completion(nil, nil)` produces the same deterministic upstream `null-error` PlatformException. **Fix:** identical to #1 — return an `unsupported-platform` FlutterError.

## Important Issues

### 3. `getFIRAuthCredentialFromArguments` phone branch surfaces a misleading `invalid-credential` error
`packages/firebase_auth_tvos/tvos/Classes/FLTFirebaseAuthPlugin.m:880, 888-892`

The tvOS phone branch also returns `completion(nil, nil)`, but here it does **not** hang or throw `null-error` — every caller (`signInWithCredential`/`linkWithCredential`/`reauthenticateWithCredentialApp:2228`) guards `if (credential == nil)` and returns `invalid-credential`. So the failure is graceful, but the surfaced error implies "you passed bad data" rather than "phone credentials are unavailable on tvOS." **Fix:** return a distinct `unsupported-platform` error from this branch so the caller-side message is honest.

### 4. Messaging: `onMessage` and `onMessageOpenedApp`/`getInitialMessage` are silent no-ops on tvOS (undocumented at the API surface)
`packages/firebase_messaging_tvos/tvos/Classes/FLTFirebaseMessagingPlugin.m:417-436` (foreground `onMessage`), `:482-532` + `:386-389` (tapped-notification / opened-app).

Both are compiled out on tvOS for real SDK reasons (`UNNotificationContent.userInfo` is `API_UNAVAILABLE(tvos)`; tvOS has no notification-tap model). Neither hangs — completion handlers still fire and `getInitialMessage` resolves to nil. But the `FirebaseMessaging.onMessage` / `onMessageOpenedApp` streams **silently never emit** with no unavailability signal. Documented in the PORTING_REPORT but should be surfaced to consumers (README already covers messaging limitations — confirm these two rows are explicit).

### 5. Missing `pubspec_overrides.yaml` — the four leaf packages can't `pub get` / publish standalone
Every leaf pubspec (`firebase_auth_tvos`, `cloud_firestore_tvos`, `firebase_storage_tvos`, `firebase_messaging_tvos`) declares `firebase_core_tvos: ^0.0.1` as a **hosted** constraint, with a comment saying "local development resolves it via pubspec_overrides.yaml until it's published." **No `pubspec_overrides.yaml` exists anywhere in the PR** (no melos.yaml, no workspace root pubspec either).

- **Example apps are fine** — they use explicit `path:` deps (`firebase_core_tvos: { path: ../../firebase_core_tvos }`), so `flutter-tvos build` on the examples works on a fresh checkout.
- **Leaf packages standalone are not** — a bare `flutter pub get` / `flutter test` / `pub publish --dry-run` inside a leaf package will fail to resolve `firebase_core_tvos 0.0.1` from pub.dev (unpublished). This also means the placeholder tests can't run in-tree for the 4 dependent packages.

**Fix:** commit the `pubspec_overrides.yaml` files, or document that they must be created locally, and confirm the intended publish order (core first — already noted in the PR body).

### 6. Auth README marks methods ✅ that were only compile-verified, not runtime-verified
`packages/firebase_auth_tvos/README.md` shows ✅ for Sign in with Apple, email-link, custom-token, email-reset, etc. The PORTING_REPORT only runtime-verified `signInAnonymously` end-to-end (simulator + real Apple TV 4K). The README conflates "compiles & links" with "works." Consider annotating which rows are runtime-verified vs. compiled-only.

### 7. Storage / messaging examples pin plugins with no tvOS implementation (resolution unverified)
`firebase_storage_tvos/example` keeps `image_picker` / `image_picker_for_web` / `web`; `firebase_messaging_tvos/example` keeps `flutter_local_notifications: ^21.0.0`. These throw `MissingPluginException` at runtime on tvOS (author-acknowledged), but more importantly their **resolution** against the monorepo's pinned Flutter SDK wasn't re-verified — the auth example's own comment notes similar deps (`font_awesome_flutter`) broke against the pinned SDK. Run `flutter pub get` on both examples to confirm.

## Passed Checks (verified clean — do not re-flag)

- **Native Firebase SDK version alignment** — all 5 podspecs pin `Firebase/* ~> 12.15.0`; upstream FlutterFire (firebase_core 4.11.0, auth 6.5.4, firestore 6.6.0, storage 13.4.3, messaging 16.4.1) all resolve to Firebase SDK **12.15.0** via `firebase_core/ios/firebase_sdk_version.rb`. tvOS floor 15.0 matches upstream `s.ios.deployment_target = '15.0'`. *Independently confirmed by the maintainer and the packaging agent.*
- **Pigeon wire ABI** — vendored `messages.g.m` = Pigeon v26.3.4 = upstream's generator version. Message format matches.
- **Auth launch-crash fix** — all 49 Pigeon HostApi selectors asserted via `NSCAssert([api respondsToSelector:])` in `firebase_auth_messages.g.m` have a tvOS-reachable implementation; MFA/TOTP methods kept as `#if TARGET_OS_TV` stubs (never removed). No missing selector → no launch SIGABRT. All stubs complete their callback.
- **Messaging co-install compile fix** — `[[FIRAuth auth] canHandleNotification:]` correctly gated `#if __has_include(<FirebaseAuth/FirebaseAuth.h>) && !TARGET_OS_TV`. Verified against `AppleTVOS26.5.sdk` + FirebaseAuth `Auth.swift` (`canHandleNotification` is `#if os(iOS)`).
- **Messaging UserNotifications guards** — every tvOS-unavailable symbol (`content.userInfo`, `UNNotificationResponse`, `didReceiveNotificationResponse:`, launch-options key, ~10 settings properties) is guarded; `unifdef` preprocessing for `TARGET_OS_TV=1` leaves zero surviving uses. `@-1` settings keys exactly match the Dart decoder's key set.
- **Import repointing** — no `#import "../` relative-parent imports, no `<firebase_core/…>` self-imports, no `s.dependency 'firebase_core'` (iOS-only) leftovers, no `Flutter` pod dependency in any of the 5 firebase packages. Storage's `Package.swift` correctly deleted; Swift imports `firebase_core_tvos`.
- **Firestore native** — byte-clean copy, zero tvOS disables needed; Pipeline API correctly gated on `FLT_PIPELINE_AVAILABLE` with a fallback that returns a real `parse-error` FlutterError (no hang).
- **Dart declaration shape** — `pluginClass`-only, no `implements:`, no `dartPluginClass:` is **correct** for this toolchain: `flutter-tvos/lib/tvos_plugins.dart` never reads `implements:`; `hasMethodChannel() => pluginClass != null` drives native registration; the Firebase packages have no Dart impl to register. Matches the repo's 11 existing `_tvos` packages.
- **`dummy.m`** — empty (license header only); matches upstream firebase_core byte-for-byte. Standard CocoaPods empty-compilation-unit trick, not cruft.
- **No secret leak** — all `firebase_options.dart` contain placeholders; no service-account JSON / PEM / `private_key` anywhere.
- **README limitation matrices** — auth (MFA/phone/OAuth/reCAPTCHA ❌) and messaging (onMessage/interaction ❌) limitations ARE documented consumer-facing in the READMEs, not just the PORTING_REPORTs.

## Summary

- **Critical / High-severity:** 2 (both the phone-auth `completion(nil, nil)` sites; see the reviewer severity note — deterministic `null-error` throw, but narrow blast radius since phone auth is unusable on tvOS regardless)
- **Important:** 5
- **Minor:** 11
- **Recommendation: APPROVE WITH CHANGES.** The engineering is sound and unusually well-verified (live round-trips on simulator + physical Apple TV 4K under AOT). The single silent-failure class in the whole PR is the phone-auth `completion(nil, nil)` pattern (#1, #2, and the milder #3) — a ~4-line-each fix that just needs to match the `unsupported-platform` `FlutterError` the sibling MFA stubs already use 30 lines away. #5 (missing `pubspec_overrides.yaml`) should be resolved before publishing. #4/#6/#7 are documentation/verification hygiene. Everything else is minor polish. Notably, the silent-failure audit confirmed these are the **only** callback sites across all five plugins that don't complete cleanly — everything else is verified sound.
